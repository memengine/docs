## Endpoint

```http
POST /v1/memories/retrieve
```

## Authentication

```http
Authorization: ApiKey mem_live_xxx
Content-Type: application/json
```

## Request body

```json
{
  "external_user_id": "customer-123",
  "query": "How should I respond to this user?",
  "limit": 5,
  "categories": ["preference", "goal"],
  "time_filter_days": 30,
  "as_of": null,
  "format": "bullets",
  "context_max_tokens": 500
}
```

### Fields

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| `external_user_id` | `string` | Yes | End-user identifier inside your tenant |
| `query` | `string` | Yes | Natural-language retrieval query |
| `limit` | `integer` | No | Default `10`, max `50` |
| `categories` | `MemoryCategory[]` | No | Optional category filters |
| `agent_id` | `string \| null` | No | Optional agent filter |
| `time_filter_days` | `integer \| null` | No | Return only memories created in the last N days |
| `preference_context` | `PreferenceReadContext \| null` | No | Explicit applicability and property keys; backend enablement required; cannot combine with `as_of` |
| `as_of` | `string \| null` | No | Historical validity boundary; ISO 8601 timestamp with timezone |
| `format` | `"bullets" \| "json" \| "xml"` | No | Default `bullets` |
| `context_max_tokens` | `integer` | No | Default `500`; max context budget for `system_prompt_addition` |

## Response schema

### Top-level fields

| Field | Type | Meaning |
| --- | --- | --- |
| `retrieval_id` | `string \| null` | Stable id used when sending retrieval feedback |
| `data` | `MemorySearchResult[]` | Ranked memory results |
| `cached` | `boolean` | Whether retrieval came from the hot cache |
| `system_prompt_addition` | `string` | Prompt-ready memory context |
| `context_token_count` | `integer \| null` | Token count of the built context when available |
| `memories_from_hot_tier` | `integer` | Number of returned memories served from Redis hot tier |
| `clarification_question` | `string \| null` | Optional user-facing question for resolving a pending conflict |
| `clarification` | `MemoryClarification \| null` | Structured id, question, expiry, and backend-approved answer options for the same clarification |
| `source_reviews` | `MemorySourceReview[]` | Up to three recent non-activating reviews; defaults to `[]` and is empty for historical `as_of` requests |
| `memory_visibility` | `object \| null` | `processing` or `unavailable`; stop dependent answers even if records/prompt text are present |
| `preference_scope_request` | `object \| null` | Application scope selection required |
| `preference_decisions` | `array` | Unresolved current-choice decisions; do not invent a current value |
| `preference_reviews` | `array` | Separate typed-preference review cards; not the source-review answer contract |
| `quota_mode` | `"FULL" \| "PASSTHROUGH" \| "DEGRADED_RETRIEVE" \| "BLOCKED"` | Current quota behavior |
| `is_degraded` | `boolean` | `true` when retrieval is degraded |
| `is_passthrough` | `boolean` | `true` when memory context should be skipped |
| `request_id` | `string` | Trace id |
| `timestamp` | `datetime` | Response timestamp |

## Which fields stop an answer?

For an answer that depends on MemoryOS state, inspect the first group before constructing the model request. The second group supports UI/telemetry; it does not independently authorize or forbid inference.

| Answer decision | Application behavior |
| --- | --- |
| `memory_visibility` is present | Stop the dependent answer; show processing/unavailable status |
| `preference_scope_request` is present | Obtain explicit applicability from the application/user |
| `preference_decisions` is nonempty | Resolve the current choice before asserting its value |
| Passthrough or no records, without a hold | Use a no-memory path only if this question can be answered without memory |

| UI or diagnostic field | How to use it |
| --- | --- |
| `source_reviews`, `preference_reviews` | Show separate versioned decision cards; never inject pending previews as facts |
| `clarification`, `clarification_question` | Show the offered choices in chat; do not guess the disputed value |
| `is_degraded`, `quota_mode`, `cached`, request IDs | Inspect operating mode and diagnostics; these do not override a hold |

A card can accompany a visibility hold. Its presence alone is not a blanket stop for unrelated questions, and its absence is not proof that a held fact is safe. Check the decision signals first. See [the chat lifecycle](/guides/chat-lifecycle) for processing-state UX.

## Check visibility before model inference

Apply [the visibility gate](/concepts/degradation) before consuming `data` or `system_prompt_addition`. A successful HTTP response, a completed job or a nonempty prompt is not permission to answer from unavailable state. Typed reads also require handling `preference_scope_request` and `preference_decisions`.

## Resolve a clarification in your existing chat

Show the backend-provided choices in your existing chat and submit the actual user selection. See [the clarification answer endpoint](/api-reference/clarifications) for the complete request, response and refusal contract.

## Review an uncertain source statement in your existing chat

Present `source_reviews` as separate decision cards, including during a hold. Use the actual user choice and the card's opaque version. See [the source-review answer endpoint](/api-reference/source-reviews) for `keep_current`, `restate`, `dismiss` and stale/busy handling. Pending previews are not active model context.

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | `string` | Memory id |

| `importance_score` | `float` | Current importance score after lifecycle adjustments |
| `last_accessed` | `datetime \| null` | Last access timestamp |

## Send retrieval feedback

Use [retrieval feedback](/api-reference/retrieval-feedback) to report use, relevance or an actual user correction. Feedback is asynchronous; a correction receipt is not proof that current memory changed.

## `format` examples

The `format` value controls how MemoryOS renders both `context_snippet` and `system_prompt_addition`.

### `bullets`

```json
{
  "format": "bullets"
}
```

```text
What you know about this user:
- User prefers concise technical explanations and Python examples.
```

### `json`

```json
{
  "format": "json"
}
```

```json
{
  "memories": {
    "preference": [
      "User prefers concise technical explanations and Python examples."
    ]
  }
}
```

### `xml`

```json
{
  "format": "xml"
}
```

```xml
What you know about this user:
<memory_context>
  <memory category="preference">
    User prefers concise technical explanations and Python examples.
  </memory>
</memory_context>
```

## Context token limit

Use `context_max_tokens` to limit the size of `system_prompt_addition`.

```json
{
  "external_user_id": "customer-123",
  "query": "How should I answer this user?",
  "limit": 10,
  "format": "bullets",
  "context_max_tokens": 300
}
```

MemoryOS drops lower-importance memories first when the context is too large. It does not truncate mid-sentence.

## Domain-aware retrieval

If a tenant has a domain schema enabled, the same retrieve endpoint returns domain-aware context in `system_prompt_addition`.

For example, an EdTech tenant may receive tutoring context about exam goals, weak topics, learning style, or forgetting-stage review urgency.

The request shape does not change:

```json
{
  "external_user_id": "student_123",
  "query": "teach this student trigonometry identities",
  "limit": 8,
  "context_max_tokens": 600
}
```

Use optional domain profile endpoints only when you need structured UI data, not for normal model calls.
