## Choose the correct access path

| Integration | Authentication | Who selects the owner? |
| --- | --- | --- |
| Server-side Python, TypeScript or native API | Tenant API key | Your authenticated application supplies `external_user_id` |
| Public authenticated MCP gateway | Gateway sign-in and backend-validated bearer identity | Server derives the tenant and user from the signed-in workspace/subject |
| Private MCP sidecar | Server-side tenant API key | Your trusted application uses its normal tenant owner mapping |

Public MCP sign-in is not the disabled-by-default Memory Passport universal-memory flow. Do not substitute one credential type for another.

## Tenant API keys

```http
Authorization: ApiKey mem_example_placeholder
Content-Type: application/json
```

Use the exact `ApiKey` scheme for tenant API routes. A raw key, `Bearer mem_...` or `X-API-Key` is not an alternative. Never put a tenant key in browser/mobile code, a public repository, screenshots or a submission.

Create API keys in your workspace dashboard. Dashboard sign-in and server-side API authentication are separate access paths.

## Stable user identity

Your application authenticates the user, then resolves a stable pseudonymous owner:

```json
{"external_user_id": "synthetic-customer-123"}
```

The key supplies the tenant identity. Resolve owner IDs **on your server**; an API key can act for owners within its permitted tenant, so arbitrary browser-supplied IDs are not end-user authorization. Use the same mapping across sessions and services. A conversation ID identifies a conversation, not a person.

For public MCP, do not provide an `external_user_id` or use a project selector to choose another person. Identity is server-derived from the authenticated user and active workspace. Use the MCP URL and sign-in instructions supplied for that deployment.

## Permissions

| Permission | Purpose |
| --- | --- |
| `read` | Authorized retrieval/list/detail/job reads |
| `write` | Admission and supported user-review decisions |
| `delete` | Destructive memory/cleanup operations |
| `admin` | Tenant administration and eligible service-correction operations |

Use least privilege. Application clients need only the permissions required for their work; operator review does not justify distributing an administrator key. Registered service writers may also bind a particular credential and authority policy. A service name or metadata field alone cannot grant authority.

## Configure an SDK

```python
import os
from memoryos import Memory

client = Memory(
    api_key=os.environ["MEMORYOS_API_KEY"],
    base_url=os.environ["MEMORYOS_API_URL"],
)
```

TypeScript takes the base URL as the second positional string argument: `new MemoryOS(key, apiUrl)`. Use the backend root without `/v1`; dashboard and MCP gateway URLs are not native API base URLs.

## Troubleshooting

- **401:** verify endpoint, key scheme, current key and workspace. Do not paste secrets into a report.
- **403:** check permissions, blocked owner and writer binding with the owner; do not bypass them.
- **Workspace not ready:** verify the intended signed-in workspace and backend access. A fresh organization token may be needed after a workspace change.
- **Connection refused/unreachable:** report an access blocker. Do not create another key to repair a stopped API.
- **Feature unavailable:** check that your backend version and configuration enable that contract; an SDK field alone does not enable it.

Memory Passport and `/v1/universal/*` remain a separate disabled-by-default private-beta contract. See its [reference](/concepts/memory-passport) only when integrating an explicitly enabled Passport deployment; ordinary tenant integration requires no global-agent registration or universal consent.
