MemoryOS is a backend for persistent assistant context. Applications submit conversations or registered service events, then retrieve governed context before answering. MemoryOS records provenance, handles competing candidates and exposes review and visibility signals.

## The application loop

1. Authenticate the user in your application and resolve a stable owner ID on your server.
2. Submit authorized evidence with `add()`. Save its original job ID; queued means admitted, not applied.
3. Inspect that job when verifying storage. A completed job can create records, retain pending candidates or create no memory.
4. Retrieve for the same owner and the intended scope.
5. Check visibility and scope/choice decisions **before** using records or calling a model for an answer that depends on them.
6. Show review cards separately in the existing chat. Submit only the user's actual choice.

See [Visibility and fallback](/concepts/degradation) for the handling of unavailable context. An empty result and a governance hold are different states.

## What your application still owns

- Authentication, project access and mapping identities consistently across clients and sessions.
- Choosing explicit property, value and applicability when using the typed preference contract.
- Business records and actions: billing, refunds, permissions and transactions remain in your systems.
- Deciding whether an answer can proceed without memory, and grounding the model's final answer.

Retrieved memory is data, not authorization or instructions that override your application's policies. Natural-language extraction and semantic matching use models; they do not guarantee that every paraphrase or project name is interpreted correctly. Typed scope is an application declaration, not a permission grant.

## Available paths and boundaries

Normal tenant integration uses an API key and a stable `external_user_id`. Public authenticated MCP instead derives identity from the signed-in user and workspace. These are separate from Memory Passport, which remains disabled by default.

Explicit preference declarations require backend enablement and the agreed property catalog. Registered service events require configured service writers and authority rules. Review and operator correction are different workflows; ordinary application keys should not receive administrative permissions.

The beta includes source attribution, current-state retrieval, lineage and versioned review contracts. It is not a general document RAG replacement or a promise of automatic truth selection, arbitrary natural-language project isolation, or production readiness.
