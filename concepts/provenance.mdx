Provenance records where a candidate came from. Authority policy decides what that source is allowed to change. Neither proves that an extracted sentence is true or that an arbitrary paraphrase was matched to the right business field.

## Conversation evidence and service events

| Path | Input | Authority boundary |
| --- | --- | --- |
| Conversation | Actual user/assistant turns, stable conversation/turn IDs | Assistant text is not direct user confirmation |
| MCP client assertion | Client-supplied conversation/declarations | Client cannot grant itself higher authority |
| Registered service | Authenticated writer, stable event ID, observed time, declared scope/evidence | Tenant-configured writer policy and credential binding |
| Explicit preference | Application-selected property, value and applicability | Versioned identity/target validation; application owns intent and scope selection |

Do not add `source` merely to make a chatbot's answer authoritative. Do not relabel tool or document text as user input. Retrieved memory is not permission to perform an external action.

## Register writers before sending events

An authorized tenant operator registers each writer, for example through `POST /v1/tenant/service-writers`. Writer definitions include `service_key`, display name, category authority rules and optional bound key. Use separate least-privilege credentials for independent services. Normal applicants should ask the owner to provision this catalog rather than receive an admin key.

A service event passed to `add()` has this shape:

```json
{
  "service": "billing-service",
  "event_id": "synthetic-subscription-event-1",
  "observed_at": "2026-11-24T09:00:00Z",
  "scope": {"account_id": "synthetic-account-1"},
  "evidence": [{"source_type": "subscription_record", "reference": "synthetic/subscriptions/1"}]
}
```

`observed_at` is required by the native request schema; SDK source helpers can supply a timestamp. Send your actual observed time when available, not a fabricated newer time to win a conflict. Evidence references identify your own records; do not include secrets.

Service `scope` participates in the source-governance path. It is not an ACL and does not automatically establish the typed project-preference read contract. See [explicit scope](/guides/scoped-preferences).

## Selection and review

The backend uses evidence eligibility, source policy, authority, temporal checks and candidate/current-state validation. Model relation/extraction output does not itself grant authority. Confidence or arrival order is not permission to overwrite a stronger source, and a retained candidate is not active memory.

Some supported transitions apply automatically; uncertain or conflicting candidates can remain pending. Inspect the original job, actual current records, provenance and visibility signal. Do not assume all equal-priority conflicts expose the same UI or that every disagreement creates a usable review.

There are separate decision paths:

- [Source review](/api-reference/retrieve#review-an-uncertain-source-statement-in-your-existing-chat): a user-facing versioned card; no direct activation of pending text.
- A/B clarification: backend-approved choices in the existing chat.
- [Service correction](/api-reference/service-corrections): an administrator's explicit candidate/target preview and apply/decline decision for eligible service events.

Use the path returned/supported for that candidate. Giving a caller an admin key is not a workaround for a missing user-facing action.

## Traceability

Current records can include `source_event_id` and `provenance`, including writer/service, event, observed time, scope and evidence metadata. Preserve returned memory/source IDs. Legacy records may have incomplete provenance; absence is not proof of a trusted source.

`GET /v1/tenant/source-events` supports authorized source inspection. Native memory detail/history and exports support management/audit use. These historical records must not be substituted for withheld current answer context.

## Replay and retention

Retry source events with the original stable event and authorized payload; changing its binding can conflict. Use an idempotency key for the eligible admission path and inspect the original job. See [the durable receipt boundary](/api-reference/add#retry-and-replay-boundary).

Raw payload retention, receipt retention, memory history and explicit user/tenant deletion are separate policies. Hash retention proves byte binding, not semantic correctness, permanent retention or permanent duplicate prevention. Admission replay alone is not proof of one worker mutation.
