Check the retrieval response before constructing a model request. HTTP 200 means the request was served; it does not mean current context is available.

## Which fields stop an answer?

For an answer that depends on MemoryOS state, inspect the first group before constructing the model request. The second group supports UI/telemetry; it does not independently authorize or forbid inference.

| Answer decision | Application behavior |
| --- | --- |
| `memory_visibility` is present | Stop the dependent answer; show processing/unavailable status |
| `preference_scope_request` is present | Obtain explicit applicability from the application/user |
| `preference_decisions` is nonempty | Resolve the current choice before asserting its value |
| Passthrough or no records, without a hold | Use a no-memory path only if this question can be answered without memory |

| UI or diagnostic field | How to use it |
| --- | --- |
| `source_reviews`, `preference_reviews` | Show separate versioned decision cards; never inject pending previews as facts |
| `clarification`, `clarification_question` | Show the offered choices in chat; do not guess the disputed value |
| `is_degraded`, `quota_mode`, `cached`, request IDs | Inspect operating mode and diagnostics; these do not override a hold |

A card can accompany a visibility hold. Its presence alone is not a blanket stop for unrelated questions, and its absence is not proof that a held fact is safe. Check the decision signals first. See [the chat lifecycle](/guides/chat-lifecycle) for processing-state UX.

## Decision order

| Signal | Meaning | Application behavior |
| --- | --- | --- |
| `memory_visibility` / `memoryVisibility` | `processing` or `unavailable`, scoped to `affected_context` or `user_learned_context` | Stop answers/actions that depend on that context; show the status or a safe fallback |
| `preference_scope_request` / `preferenceScopeRequest` | Application must select applicability | Obtain a scope from the application/user; do not guess from chat wording |
| Nonempty `preference_decisions` / `preferenceDecisions` | Current choice unresolved | Obtain an explicit choice before claiming a current value |
| `is_passthrough` / `isPassthrough` | Memory bypassed | Use no memory; continue only if the request can be answered without it |
| No records, no hold | No context returned | Do not invent recall; ask or answer without memory as appropriate |
| Records, no hold | Context available | Use returned context as data, preserve citations and apply your answer policy |

`is_degraded` alone is not a visibility hold. Conversely, a hold takes precedence over records, prompt text, cache flags or an application's earlier copy of the context. Do not substitute historical client copies for withheld current state.

## Minimal Python gate

```python
def memory_gate(result):
    if result.memory_visibility is not None:
        return "held"
    if result.preference_scope_request is not None:
        return "scope_required"
    if result.preference_decisions:
        return "choice_required"
    if result.is_passthrough:
        return "bypassed"
    return "available" if result.items else "empty"
```

Only after this gate should your application construct a dependent model request. If retrieval fails, its state is unknown: do not silently reuse old memory. An unrelated question may proceed without memory under your own policy; a question such as "what is my current preference?" should receive an unavailable/unknown response instead of a guessed answer.

## Review cards during a hold

`source_reviews` may still contain safe decision cards. Show them separately to the authenticated user in the existing chat. Their previews and pending text are **not** active records and must not be copied into `system_prompt_addition` or treated as accepted facts. A card does not authorize the model to choose an action.

See [the review answer contract](/api-reference/retrieve#review-an-uncertain-source-statement-in-your-existing-chat) and [MCP](/sdk/mcp). After an actual decision, retrieve again; a submitted action alone is not proof that recall is restored.

## Quota and dependency modes

| Mode | Meaning |
| --- | --- |
| `FULL` | Normal quota mode |
| `PASSTHROUGH` | Memory context bypassed |
| `DEGRADED_RETRIEVE` | Retrieval reduced |
| `BLOCKED` | Writes blocked by quota governance |

Operational headers include `X-MemoryOS-Quota-Mode`, `X-MemoryOS-Budget-Remaining`, `X-MemoryOS-Quota-Reset`, `X-MemoryOS-Circuit-Status` and `X-MemoryOS-Processing`. These do not override response visibility or authorization checks.

See [Webhooks](/guides/webhooks) for operational notifications and [Rate limits](/concepts/rate-limits) for retry handling. Neither a quota-mode header nor a webhook confirms a particular memory mutation.
