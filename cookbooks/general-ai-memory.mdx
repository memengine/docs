Use the [quickstart](/quickstart) for runnable SDK examples and the [applicant guide](/guides/applicant-setup) for assigned access. This workflow uses tenant memory; it does not require Memory Passport or global-agent registration.

## Application flow

1. Authenticate the user and resolve a stable owner on your server.
2. Retrieve for that owner and selected applicability.
3. Apply the [visibility/scope/choice gate](/concepts/degradation).
4. If context is available, construct the model request using returned context as data. Keep reviews in separate chat controls.
5. Preserve actual conversation evidence. Submit meaningful turns once, with stable conversation/turn IDs and a saved idempotency key.
6. Track the original job and later reads when verifying persistence. Reopening the chat keeps the same owner mapping.

For a user correction, use the supported review or [explicit replacement](/guides/scoped-preferences) path. Do not make a memory-dependent answer from old context while the correction is held or processing. A retrieval error leaves state unknown; it is not proof that old memory remains current.

## Model examples

- [OpenAI](/guides/openai): guarded Python inference using existing backend state.
- [Anthropic](/guides/anthropic): the same gate before provider inference.
- [TypeScript SDK](/sdk/typescript): equivalent field names and read gate.

Those examples use an explicitly configured model. They are not a guarantee that the model obeys the memory, resolves arbitrary contradictions or gives grounded answers. Quote fidelity, backend state correctness and semantic answer correctness are different checks.

## Decide whether memory helps

Record setup/integration effort, custom logic and operational dependencies. Compare with an implementation using your own database and policy logic. Passing a synthetic workflow is useful integration evidence, not proof that developers need this service or that it outperforms every alternative.
